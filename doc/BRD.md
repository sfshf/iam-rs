# IAM 业务需求文档

## IAM一般用于什么场景？

**IAM（Identity and Access Management，身份与访问控制）** 是现代企业信息化和云计算的基础设施。简单来说，只要系统需要解决**“你是谁（认证）”**、**“你能做什么（权限）”** 以及 **“谁把你加进来的（审计/管理）”** 这三个核心问题，就需要 IAM。在业界，IAM 根据服务对象的不同，主要分为以下四大经典应用场景：

### 一、 EIAM (Employee IAM)：企业内部员工身份管理

这是最传统也是最基础的场景，主要解决企业内部**打卡、安全、效率**的问题。

- **统一身份源（Single Source of Truth）：** 企业员工入职时，HR 在系统（如飞书、钉钉、AD域）中创建账号，IAM 会自动把这个账号同步到公司的邮箱、代码库（GitLab）、财务报表等所有内部系统中。
- **单点登录（SSO）：** 员工只需要登录一次（通常结合扫码或安全硬件），就可以免密访问公司所有的内部系统，不再需要记几十个密码。
- **入离调转自动化（Lifecycle）：** 当员工转岗时，自动调整其系统权限；当员工离职时，在 IAM 侧一键禁用账号，该员工对公司所有系统的访问权限瞬间被全部切断，防止数据泄露。

### 二、 CIAM (Customer IAM)：面向最终用户的身份管理

当企业需要管理**外部客户、APP 用户、网站注册会员**时，使用的就是 CIAM。

- **多渠道无缝登录：** 支持手机验证码、微信扫码、支付宝登录、Apple ID 登录等现代认证方式，追求极高的并发性能和极低的延迟。
- **安全性与风控拦截：** 在用户登录时进行风险评估。如果是异地登录或密码多次输错，IAM 会自动触发 **MFA（多因素认证）**，要求输入动态验证码，防止撞库和盗号。
- **隐私与合规（如 GDPR）：** 管理用户的隐私授权协议。用户可以在个人中心查看、撤回自己授予 APP 的权限，满足国家的法律合规要求。

### 三、 SaaS 与多租户场景：B 端商业化产品的基础中台

如果您正在开发一款需要卖给不同企业客户的 **SaaS 软件（如 CRM、ERP、协作工具）**，IAM 是其核心的权限引擎。

- **租户物理/逻辑隔离：** 确保 A 公司的管理员登录后，只能看到 A 公司的员工和数据，绝对无法越权看到 B 公司的数据（即通过前文讨论的 `tenant_id` 隔离）。
- **租户自主控权：** SaaS 平台不需要为客户手动分配权限，而是把 IAM 的后台权限树（如基于 Casbin 的 RBAC 模型）开放给客户的系统管理员，由他们自己去定义公司内部的岗位和权限。

### 四、 云原生与微服务场景：API 密钥与机器身份管理（Non-human IAM）

在现代微服务和云原生架构中，IAM 的服务对象已经不仅仅是“人类”，还包括**程序、服务器、微服务和设备**。

- **微服务间零信任（Zero Trust）：** 在微服务群中，订单服务不能无条件信任支付服务。支付服务在调用订单服务前，必须向 IAM 获取一个临时凭证（如短期 JWT 或 mTLS 证书），订单服务通过网关验签后才允许访问。
- **开放平台与开发者 API Key：** 当您的系统需要像开放平台一样，允许外部开发者写脚本或通过 CLI 命令行工具对接时，IAM 负责生成、校验、吊销这些开发者的 `AccessKey / SecretKey`（类似于 AWS IAM）。

### 💡 核心价值总结

无论是上述哪种场景，引入专业的 IAM 系统都能带来三个核心价值：

1. **安全合规：** 满足国家等保、金融审计要求，所有权限变更和登录操作必须留存**审计日志（Audit Logs）**。
2. **研发解耦：** 业务开发团队再也不用为每个新微服务重复编写“用户表、密码加密、登录拦截、角色判断”的代码，直接交给 IAM 和网关即可。
3. **用户体验：** 一人一号，通行全网。
