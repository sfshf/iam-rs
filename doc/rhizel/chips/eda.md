# Event-Driven Architecture

## 事件朔源架构，我要存事件，如何才能将存储变得很小？

在事件溯源（Event Sourcing）架构中，事件是只增不减（Append-Only）的，随着业务增长，存储压力会非常大。由于事件代表的是“发生过的事实”，其结构通常非常适合进行极致压缩。

要将事件存储变得极小，可以从**数据序列化**、**应用层架构设计**和**存储层优化**三个维度来实现：\*\*

### 1. 极致的序列化：改用 Protobuf

如果您目前使用的是 JSON 或 XML 存储事件，切换到 **Protocol Buffers (Protobuf)** 可以立刻让存储体积缩小 **50% 到 80%**。

- **去掉键名（Key）：** JSON 每一条数据都要重复存储 `"user_id"`、`"event_time"` 等字符串。Protobuf 在传输和存储时只保存**字段编号 (Field Numbers)**（如 `1`, `2`），不包含任何属性名。
- **Varint 变长编码：** Protobuf 对整数采用变长编码。例如数字 `1` 在 JSON 中占 1 字节，在整数类型中可能占 4 字节，而 Protobuf 仅占 **1 字节**；越小的数字占用的空间越小。
- **利用最佳性能区：** 正如前面提到的，将事件中最高频的字段（如 `event_id`, `aggregate_id`, `timestamp`）的序号设在 **1 到 15** 之间，每个字段的 Tag 仅占 1 字节。

### 2. 架构层优化：快照机制（Snapshotting）与冷热分离

事件溯源的核心是“用事件重放还原状态”，但我们不需要把几年前的每一个细微事件都永远用最昂贵的存储方案保存：

- **定期截断与快照（Snapshot）：**
  - 每隔 1000 个事件，计算出当前的最新状态，存为一个“快照”。
  - 有了快照后，**历史的旧事件在业务上就不再需要频繁读取。**
- **冷热分离（Data Tiering）：**
  - **热数据（最新快照 + 最新事件）：** 存放在高性能、低延迟的数据库（如 Kafka, EventStoreDB, PostgreSQL）中。
  - **冷数据（历史事件归档）：** 将归档的旧事件打包（如按天或按聚合根 ID），使用 **Gzip / Zstd** 算法进行高压缩比压缩，直接倾倒到**低成本的对象存储**（如 AWS S3 Glacier、阿里云 OSS 冷归档）中。此时的存储成本几乎可以忽略不计。

### 3. 数据结构精简：只存“增量变动”

在设计 .proto 事件文件时，避免存入冗余信息：

- **Delta 状态（仅存变更）：** 不要在 `UserUpdatedEvent` 中把整个用户对象再存一遍。只存储被修改的字段（例如只存改变后的 `nickname`）。
- **拒绝冗余元数据：** 诸如操作人的 IP 地址、浏览器 User-Agent 等审计日志信息，应当与核心业务事件解耦，单独存入低成本的日志系统（如 ELK / Loki），不要混在事件存储中。

### 4. 存储引擎层：选择列式存储或专用压缩

如果您需要对历史事件进行大数据分析，将事件推送到分析型数据库时：

- **采用列式存储（Columnar Storage）：** 如 **Parquet** 或 **ClickHouse**。
- **原理：** 列式存储将相同字段的数据聚合在一起存储。因为同一个字段的数据类型和内容高度相似（例如一整列都是时间戳或事件类型），**压缩率会产生质的飞跃**，通常可以达到 10:1 甚至更高的压缩比。
